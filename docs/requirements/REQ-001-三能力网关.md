# REQ-001:三能力网关

## Scenario

舰队 agent 经 lan-mac 网关(overcast)用智谱 GLM:单 token 限流或欠费即断供,需要双 token failover;system prompt 需要热改注入(不停服);全量请求要可回溯观测(ClickHouse)。三能力按上游 CLIProxyAPI 配置态优先达成(ADR-0001),本 REQ 登记验收判据。

## Criteria

### 能力一:failover 双 token(判据实写,依据 research-01 已落节)

- [x] 智谱两组各挂两把 key:openai-compatibility(chat 面,base `https://open.bigmodel.cn/api/paas/v4`)用 `api-key-entries` 两行;claude-api-key(messages 面,base `https://open.bigmodel.cn/api/anthropic`)拆两条目、每条一个 `api-key`(实测该组不认 `api-key-entries`);两组显式 `disable-cooling: false`(2026-10-11 lan-mac 部署实测,起服日志 2 Claude API keys 加 2 OpenAI-compat;另补 responses 面 xai-api-key 组 2 keys,见 design-001 §1.2)
- [x] 第一把故意配错(401)加第二把有效:非流式请求得 200,日志可见先失败后换 key(2026-10-11 单 ov-03 实测:chat 组第一把尾位改错重启,同一请求 id `[98c55a49]` 先 401 warn 后 200,客户端 200;还原重启后两发干净 200)
- [ ] 400 坏请求停在第一把,不打第二把(请求错误不轮转)
- [ ] 流式在首个内容块之后掐断上游:客户端看到错误,且不会从第二把 key 续写后半段
- [ ] 客户端只见网关自己的访问 key(`access.api-keys`),两把智谱 key 不出网关
- [ ] 断 lan-mac 网络再恢复:容器起来后两把 key 仍在(配置卷与 auths 卷外置),冷却状态丢属可接受
- [ ] 同机已有别的 CPA 时,本网关不与它同时当同一批 agent 的上游(部署批核对)

### 能力二:prompt 注入热改(判据留位,待 research-01 注入三件落节后细化)

- [ ] system prompt 注入生效且可热改,不重启容器、不断在跑流(细化判据待注入三件:注入面按模型/按客户端/全局、热改通道、与 request-retry 的叠加语义)

### 能力三:CH 回溯观测(判据留位,待 research-01 CH 四件落节后细化)

- [ ] 全量请求回溯落 ClickHouse,出口异步批写,不占请求热路径(细化判据待 CH 四件:schema、全量或采样、流式 token 计、留存策略)
