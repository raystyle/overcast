# 上游选型,为什么配置态不 fork

> 类型: explanation
> 裁定: ADR-0001

## 问题

双 token failover 网关怎么达成:改上游代码、换现成网关、还是纯配置?候选四案对照见 research-01(总台在途),本页只留结论与候选表。

## 裁定一句

上游 CLIProxyAPI v8 官方镜像钉 tag 运行 + 本仓薄资产;conductor 已支持同请求换 key 加按状态码冷却,双 key 是配置问题不是能力缺失;不 fork。

## 候选

| 候选 | 裁定 | 一句话依据 |
| --- | --- | --- |
| CLIProxyAPI v8 配置态双 key | **主案** | conductor 已支持同请求换 key 加按状态码冷却;无数据库、单容器、arm64 官方镜像 |
| LiteLLM | 条件备胎 | 能力够但属第二套网关,舰队 cc/cx 别名要重接;仅当客户端只走 OpenAI chat 且不能改 CPA 配置时 |
| new-api | 不选 | 面板与数据库组件重,两把 key 用不上;渠道市场出现需求再议 |
| 自研薄层 | 不选 | Claude messages 与 Codex responses 翻译要重做;多一跳反代只为换 key 不值 |
| fork 上游 | 不选 | v8 几乎按天发版,conductor 上会反复冲突;补丁以小提交往上游提,不留分叉分支 |

**二开条件句**(唯一允许动代码的路径):智谱把余额不足或限流放在 HTTP 400、HTTP 200 body、或 `request-scoped-errors` 匹配不到的形态时,先配 `request-scoped-errors` 四档动作(stop / stop-and-cooldown / continue / continue-and-cooldown)按 body 子串分类;配置盖不住再补一个很小的分类函数(`IsRequestFault` 与 `matchRequestScopedErrorAction` 是现成钩子)。不在 HTTP 层再包重试(会与 `request-retry` 叠成双倍请求),不动 round-robin 与冷却状态机。

已见反例收窄:智谱 5 小时窗限的额度尽是标准 429 面(code 1308),内建规则即接,未触发条件句(REQ-001 演进,2026-10-12)。
